# Обновление Git Time Machine до 0.8.0

Версия 0.8 заменяет модель «один переход архивов = один огромный коммит» на реконструкцию нескольких функциональных коммитов.

## Что изменилось

После файлового и семантического анализа приложение строит карту функциональности:

```text
Продуктовые возможности
├─ Публичный сайт
├─ Заявки
├─ Электронные договоры
├─ Отзывы
├─ Ученики
├─ Личный кабинет
├─ Расписание
├─ Домашние задания
└─ Оплаты

Доступ и коммуникации
├─ Авторизация
└─ Email и уведомления

Платформа и инфраструктура
├─ Основа приложения
├─ База данных
├─ Административная панель
├─ Инфраструктура
└─ Медиа
```

Каждый изменённый файл получает один основной функциональный кластер. Если общий файл содержит код нескольких функций, он может дополнительно появиться как поддерживающий файл, но не учитывается повторно в основной файловой статистике.

## Как определяется кластер

Учитываются:

- путь и название файла;
- содержимое изменённого кода;
- найденные функции, классы и компоненты;
- маршруты, формы и API-запросы;
- SQL-таблицы, поля, индексы и связи;
- признаки авторизации, расписания, ДЗ, договоров, отзывов и других функций;
- отличие конкретного продуктового файла от общего admin/config/assets-контейнера.

Для каждого кластера сохраняются уверенность, сигналы классификации, основные файлы, общие поддерживающие файлы и семантические факты.

## Выравнивание корней архивов

Если одна версия хранится как `www/alex-educator.com/...`, а другая начинается сразу с `alex-educator.com/...`, приложение ищет наиболее вероятный общий корень, временно убирает упаковочный префикс и сравнивает реальные проектные пути. Папки резервных копий рядом с `www/` при этом не попадают в коммиты. В отчёте отображаются применённые префиксы и уверенность выравнивания.

## Защита от раздутых отчётов

Большие списки однотипных маршрутов, форм, функций и полей БД автоматически сворачиваются в понятные группы. Полные пути и доказательства остаются в JSON-отчёте.

## Установка

Распаковать патч поверх текущего проекта и выполнить:

```powershell
npm install
npm run test:core
npm run build
```

Ожидаемый smoke-тест заканчивается строкой:

```text
Core smoke test passed
```

## Важно

Полученные коммиты являются реконструкцией функциональных границ. Без исходной папки `.git` приложение не утверждает, что именно такие коммиты и именно в таком порядке существовали в настоящей истории проекта.
